Перед початком
Визнач корінь Git-репозиторію.

Перевір фактичну структуру репозиторію.
Не припускай, що перелічені у специфікації файли існують.
Використовуй поточний код як головне джерело істини.
Незмінні правила
ORGANIZE ≠ SUMMARIZE
REWRITE ≠ SHORTEN
MERGE ≠ DELETE UNIQUE CONTENT
BOOK STRUCTURE ≠ DIRECTORY LIST

Заборонено:

вигадувати файли, класи, функції, URL, settings або Docker services;
заявляти про успішні тести, які не запускалися;
видаляти унікальні пояснення, приклади, схеми, лабораторні роботи чи debugging-секції;
виконувати git commit;
виконувати git push;
приховувати основний матеріал лише в archive/;
оновлювати MkDocs-навігацію до створення канонічної структури.

Правила інспекції

Не обмежуйся назвами файлів або першими абзацами.

Для кожного документа зафіксуй:

шлях;
призначення;
рівень;
теми;
передумови;
приклади;
зв’язок із Notes Chat App;
дублювання;
суперечності;
цільовий шар;
цільову главу;
рекомендовану дію.

Для кожного важливого компонента коду зафіксуй:

фактичний шлях;
класи та функції;
вхідні дані;
результат;
залежності;
викликачів;
тести;
пов’язану документацію;
статус точності документації.
Робота з великим корпусом

Не намагайся втримати весь docs/ і archive/ в одному контексті.

Працюй пакетами:

створи повний inventory;
згрупуй файли за темами;
аналізуй одну групу;
записуй результати в audit-файли;
переходь до наступної групи;
перед написанням глави повторно відкривай її основні джерела.
Канонічний зміст

Кожна тема повинна мати одну головну теоретичну главу.

Zero to Hero та Project Deep Dive:

коротко нагадують теорію;
посилаються на канонічну главу;
зосереджуються на побудові або фактичній реалізації;
не дублюють повністю фундаментальне пояснення.
